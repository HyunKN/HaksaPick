# HaksaPick B 파트 데이터 구조 v0.2 — 쉽게 읽는 설명과 예시

> **이 문서의 목적:** B 파트가 어떤 데이터를 받아서, 어떤 상태를 관리하고, 어떤 추천 결과를 만들어야 하는지 설명한다.
>
> **확정된 것:** 사용자 승인·권한·버전 검증, 대화와 확정 설정의 분리, 추천의 출처·불확실성 등 **동작 원칙**.
>
> **아직 미확정:** 실제 DB 테이블·컬럼명, HTTP 경로, JSON 필드명·자료형, A/DB 파트의 실제 제공 데이터. 예시 JSON은 **개발용 Mock**이며 팀이 승인한 최종 스키마가 아니다.
>
> 함께 볼 문서: [PRD](PRD.md) · [API 계약 및 요청·응답 초안](API_SPEC.md) · [코드 검증 개발 절차](DEVELOPMENT_PROCESS.md).

## 1. B 파트에 필요한 데이터와 확정 여부

이 표는 **우리가 무엇을 취급하는지**, **어느 부분까지 합의했는지** 확인하는 목록이다. 실제 DB 테이블 목록이 아니다.

| 다루는 정보 | 쉬운 예시 | 지금 정해진 원칙 | 아직 결정하지 않은 것 |
|---|---|---|---|
| 사용자 기본 정보 | 컴퓨터융합학부·4학년·재학 중 | 학적 기본 정보는 주로 폼으로 입력 | 정확한 필수 항목, 값 종류, DB 컬럼 |
| 사용자가 승인한 개인 설정 | 현장실습에 관심, 국가장학금은 제외 | 승인된 DB 상태가 추천의 기준 | 최종 저장 방식·테이블 |
| 사용자가 직접 정한 세부 조건 | '학년 제한이 맞는 모집만', '외부 공모전 제외' | 조건을 개별적으로 추가·수정·삭제 가능 | 조건별 상세 필드와 표현 방식 |
| 승인 전 변경안 | '국가장학금 제외'를 추가할까요? | 승인 전에는 개인 설정을 바꾸지 않음 | 제안 만료시간, 상태 필드 |
| 최근 대화/요약 | '그 조건은 그대로 두고...'가 가리키는 내용 | 확정 설정과 대화 기억은 별도로 관리 | 대화 보존 기간·요약 시점 |
| A 파트가 전달하는 공지 | 모집 공지의 제목·본문·출처 | 출처·식별 가능 정보에 기반해 분석 | 실제 DB 스키마·제공 가능한 필드 |
| 공지 내용 분석 결과 | 이 공지는 3학년 이상 현장실습 모집 | 공지 자체의 내용은 사용자와 무관하게 분석 가능 | 분석 결과 저장 위치·재사용 정책 |
| 사용자별 추천·피드백 | A에게 추천, B에게는 자격 미달 | 관심 관련성과 지원 자격 구분 | 점수 계산·피드백 저장 구조 |

**읽는 법:** '확정된 원칙'은 지켜야 하지만, 예시 속 필드명까지 확정됐다는 뜻은 아니다.

## 2. 사용자 설정부터 공지 추천까지 데이터가 연결되는 방식

이전 문서의 '핵심 논리 구조'는 DB ERD가 아니라 **서로 다른 정보들이 어떤 관계로 사용되는지** 보여 주는 개념도다.

\`\`\`text
사용자 (로그인 / Backend가 사용자 확인)
 ├─ 승인된 사용자 설정
 │   ├─ 학적 기본 정보: 학과·학년·재학 상태 등
 │   └─ 관심 조건: 포함·제외·필수·선호 조건
 ├─ 아직 승인되지 않은 설정 변경안
 ├─ 대화 맥락: 최근 메시지·요약·미해결 질문
 └─ 추천 결과에 대한 사용자 반응

A 파트에서 받은 공지 원문
 └─ B 파트에서 공지 내용 분석
      └─ [분석한 공지] + [각 사용자의 승인된 설정]
           └─ 사용자마다 다른 추천/제외 판단
\`\`\`

**예시 흐름:** 사용자가 '현장실습 공지에 관심 있어'라고 말함 → Claude가 조건 추가를 제안 → 사용자가 승인 → Backend가 개인 설정에 저장 → A 파트에서 받은 현장실습 공지를 분석 → 사용자 설정과 비교해 추천한다.

위 연결은 **저장 위치나 테이블 관계(FK)를 확정하지 않는다.** 실제 API와 DB는 별도로 정한다.

## 3. 사용자 설정의 구성: 기본 정보와 관심 조건

여기서 **'확정 설정'은 별도의 설정 종류가 아니라 '사용자가 승인해 현재 적용 중인 설정 전체'**를 뜻한다.

| 용어 | 뜻 | 예시 |
|---|---|---|
| 기본 학적 정보 | 학교/학과/학년 등 일반적으로 정해진 정보 | 컴퓨터융합학부, 4학년 |
| 사용자 관심 조건 | 사용자가 보고 싶거나 제외하고 싶은 공지 기준 | 현장실습 포함, 국가장학금 제외 |
| 사용자 정의 '추가 조건' | 기존 기본 항목만으로 표현할 수 없는 세부 기준 | '학부생만 신청 가능한 프로그램' |
| 확정 설정 | 현재 저장되어 실제 추천에 적용되는 승인된 설정 | 위 기본 정보와 승인된 관심 조건 전체 |
| 미확정 변경안 | LLM이 제시했지만 아직 적용되지 않은 변경 | '교내 공모전만 포함' 제안 |

따라서 **추가 조건도 사용자가 승인한 순간 확정 설정에 포함된다.** '확정 설정 외부에 붙는 별도 설정'이 아니다.

**설정 JSON 예시 — 필드명·값은 미확정:**

\`\`\`json
{
  "preference_version": 3,
  "academic_profile": {
    "department": "컴퓨터융합학부",
    "year": 4,
    "enrollment_status": "enrolled"
  },
  "conditions": [
    {
      "condition_id": "cond-001",
      "scope": "notices",
      "polarity": "include",
      "strength": "preferred",
      "text": "현장실습 관련 모집"
    },
    {
      "condition_id": "cond-002",
      "scope": "notices",
      "polarity": "exclude",
      "strength": "required",
      "text": "국가장학금"
    }
  ]
}
\`\`\`

**중요:** 승인된 조건 각각에 ID를 두면 특정 조건만 바꿀 수 있다. 사용자가 조건을 추가할 때마다 DB 컬럼을 새로 만들지는 않는다. 구체적 JSON/테이블·\`scope\`·\`strength\` 값은 제안이고, 최종 스키마는 Backend/DB와 협의한다. 폼에서 수정한 기본 학적 정보를 어떤 승인·버전 정책으로 저장할지도 별도 확인이 필요하다.

## 4. 설정 추가·수정·삭제 시 승인 절차와 동시 수정 충돌

이 절은 **(1) 무엇을 변경할지 제안하는 데이터**, **(2) 사용자가 승인했을 때 저장하는 규칙**, **(3) 동시에 두 곳에서 바꿀 때 발생하는 충돌**을 다룬다. 단순히 HTTP 요청을 보내는 방법만 설명하는 절은 아니다.

### A. 변경 유형 3가지

| 사용자의 말 | 변경 종류 | 실제 동작 |
|---|---|---|
| '국가장학금 공지는 제외해줘' | \`add\` | 새 제외 조건 추가 제안 |
| '현장실습만이 아니라 인턴도 포함해줘' | \`update\` | 기존 관심 조건 수정 제안 |
| '공모전 제외 조건은 지워줘' | \`remove\` | 기존 조건 제거 제안 |

**중요:** Claude는 **제안만** 반환한다. 변경안은 Backend가 보관하고, 사용자 화면에 보여 준 뒤 승인 시에만 DB 설정을 수정한다.

\`\`\`text
사용자 메시지
  → Backend → Core(LangGraph/LangChain/Claude)
  → '추가/수정/삭제' 변경안 반환
  → Backend가 사용자에게 승인 대기 변경안 제공
  → 사용자가 승인 또는 취소
       ├─ 취소: 확정 설정 그대로
       └─ 승인: Backend가 소유권·제안 원본·버전을 검증한 뒤 저장
\`\`\`

**승인 대기 데이터 예시 — 미확정 JSON:**

\`\`\`json
{
  "proposal_id": "proposal-001",
  "base_preference_version": 3,
  "status": "pending",
  "operations": [
    {
      "operation": "remove",
      "target_condition_id": "cond-001"
    }
  ]
}
\`\`\`

API 경로와 정확한 요청/응답 형태는 [API_SPEC.md](API_SPEC.md)에서 **제안**으로 관리한다. 위의 변경안 JSON은 Backend가 검증 없이 실행할 명령이 아니다.

### B. '동시성'이란?

**두 창/기기에서 같은 설정을 동시에 편집하는 상황**이다.

- 노트북 A가 **설정 버전 3**을 읽고 '현장실습 조건 삭제'를 준비함.
- PC B도 버전 3을 읽고 '현장실습 조건 수정'을 먼저 승인함 → 서버 설정이 **버전 4**가 됨.
- A가 이전 버전 3을 기준으로 삭제 승인을 시도함.
- 서버는 **최신 설정과 충돌했다는 사실을 알리고 저장을 거부**해야 한다. 사용자는 최신 상태를 확인하고 다시 진행한다.

또 같은 승인 요청을 두 번 보내도 설정이 두 번 바뀌면 안 된다. **버전 검사·중복 방지는 Backend/DB 코드로 강제**한다. 구체적인 HTTP 오류 코드·응답 본문은 아직 미확정이다.

## 5. LLM이 이전 대화를 이해하도록 전달하는 정보 (Context Engineering)

**맞다. 이 절은 Context Engineering에 사용할 대화 데이터와 확정 설정을 구분하는 내용이다.**

예시:

- 첫 대화: '장학금은 관심 있는데 국가장학금은 제외해줘.'
- 다음 대화: '아까 제외한 건 그대로 두고 현장실습도 추가해줘.'

두 번째 문장만 Claude에 전달하면 **'아까 제외한 것'**이 무엇인지 알기 어렵다. 따라서 관련된 이전 대화와 현재 승인된 설정을 함께 전달한다.

| 전달하는 정보 | 필요한 이유 | 주의점 |
|---|---|---|
| 현재 확정 설정 | 실제 추천·변경 판단의 기준 | **DB 원본이 기준**, 요약으로 대체 금지 |
| 최근 대화 | '그거', '아까', '이 조건'의 의미 파악 | 매번 전체 대화를 보내지 않음 |
| 미해결 질문·승인 대기 변경안 | 아직 끝나지 않은 처리 이어가기 | 확정 설정과 혼동 금지 |
| 오래된 대화 요약 | 과거 맥락을 적은 토큰으로 전달 | 요약이 일부 빠져도 확정 조건은 보존 |

이것은 **무조건 모든 대화를 저장하자는 뜻이 아니다.** 저장 범위·기간·삭제 및 Compaction 시점은 미확정이며 실사용 데이터 보관 전에 결정한다.

## 6. A 파트에서 전달받아야 할 공지 정보

**이 데이터 형식은 아직 고정되지 않았다.** 현재 아래 목록은 **B 파트가 분석/추천하기 위해 필요한 의미상 정보**다. A 파트의 실제 DB 컬럼 명세를 강제하지 않는다.

| 필요한 정보 | 왜 필요한가 | 예시 |
|---|---|---|
| 공지 식별 정보 | 어떤 공지를 분석했는지 추적·중복 방지 | \`notice_id\` |
| 공지 제목 | 후보 검색과 주제 파악 | '동계 현장실습 모집' |
| 본문 | 자격·기한·조건을 원문에서 확인 | '3학년 이상 신청 가능' |
| 원문 출처 | 사용자에게 근거와 링크 제공 | 공지 URL |
| 게시 시점 | 오래된 공지 구별 | 2026-11-18 |
| 변경 식별 방법 | 수정된 공지 재분석 판단 | 버전·갱신일·내용 해시 중 가능한 방법 |

**개발용 Mock JSON (아직 팀 연동 계약 아님):**

\`\`\`json
{
  "notice_id": "example-notice-001",
  "title": "예시 현장실습 모집",
  "content": "3학년 이상 재학생을 모집합니다.",
  "source_url": "https://example.edu/notice/001",
  "published_at": "2026-11-18",
  "version": "1"
}
\`\`\`

**아직 확인할 점:** 실제로 A/DB가 어떤 필드를 제공하는지, 본문 누락/첨부만 존재하는 경우는 어떻게 표시하는지, 공지 수정·중복은 어떻게 구별하는지. 제공할 수 없는 필드는 AI가 만들어내지 않으며 결측·미확인으로 처리한다.

A 파트 크롤러의 구현·DB 구조는 여기서 건드리지 않는다. B는 실제 자료를 받으면 변환 계층에서 **우리 내부 공통 입력 형태로 매핑**하는 방식을 사용한다.

## 7. 공지 내용 분석과 사용자별 추천의 차이

**같은 공지를 모두에게 똑같이 분석할 수는 있어도, 모두에게 똑같이 추천해서는 안 된다**는 뜻이다.

가상의 공지 원문:

> '2026 동계 현장실습 참가자 모집. 3학년 이상 재학생 지원 가능.'

**1단계: 공지 내용 분석 (사용자와 무관)**

| 추출 정보 | 결과 |
|---|---|
| 유형 | 현장실습 모집 |
| 지원 자격 | 3학년 이상 재학생 |
| 기한 | 원문 예시에 없음 → 미확인 |
| 근거 | '3학년 이상 재학생 지원 가능' |

**2단계: 사용자별 개인화 판단**

| 사용자 | 승인된 설정 | 개인화 결과 |
|---|---|---|
| A — 4학년, 현장실습 관심 | 현장실습 모집을 선호 | 관심 있음. 예시의 학년 요건에는 해당 |
| B — 1학년, 현장실습 관심 | 현장실습 모집을 선호 | **관심은 있지만**, 예시의 학년 요건에는 미달 |
| C — 4학년, 현장실습 제외 | 현장실습 모집을 제외 | 신청 가능 여부와 별개로 개인 설정상 제외 |

여기서 \`relevance\`는 **관심사와 관련 있는가**, \`eligibility\`는 **신청 자격을 충족하는가**를 뜻한다. 원문에 추가 자격이 없다면 그 외 자격은 단정하지 않는다.

이 구분이 필요한 이유는 **같은 공지 분석 결과를 사용자마다 다시 추출할 필요가 없도록 재사용**하고, 이후 각 사용자의 설정과 비교하여 추천하는 비용을 줄이기 위해서다. 실제 분석 결과 저장/캐싱 방식은 아직 미확정이다.

피드백(도움·무관·저장·제외)은 이후 평가에 사용할 수 있지만 **확정 설정을 자동 변경하는 권한은 없다**.

## 8. 실제 API 연동 전에 팀과 확인할 4가지 — 질문과 사례

**B 파트 Mock 개발은 먼저 시작할 수 있다.** 아래는 **실제 Backend·A/DB·C와 연결하기 전** 합의해야 할 항목이다.

| 누구와 협의? | 확인할 질문 | 왜 필요한가? / 발생 가능한 사례 |
|---|---|---|
| **B ↔ Backend/DB** | 사용자 설정은 어떤 필드로 저장하고, 조건 ID·버전·승인 대기 상태는 누가 관리하나? | 같은 사용자가 두 창에서 다른 조건을 수정하면 **버전 충돌을 차단**해야 한다. |
| **B ↔ A/DB** | 공지 ID, 제목, 본문, 링크, 게시/수정일과 첨부를 어떤 형태로 받을 수 있나? | 공지 본문은 비어 있고 PDF 첨부만 있을 때 **분석 불가/대체 처리**를 결정해야 한다. |
| **B ↔ C/Backend** | 추천 결과에 어떤 필드를 노출하고, 자격 '불명확'과 제외 사유를 어떻게 전달하나? | C 화면에 '추천'만 표시하면 **자격 미달 공지를 잘못 권유**할 수 있다. |
| **공통** | 보존/삭제 기간, 조건 개수 상한, API 오류 형태와 호출 제한은? | 사용자가 설정 삭제를 요청하거나 Claude가 실패할 때 **데이터 삭제 범위와 오류 응답**이 일관돼야 한다. |

**우선순위:** (1) B 내부 사용자 설정/변경안과 Core 입출력 스키마 → (2) Mock 기반 실행·테스트 → (3) A/DB 실제 공지 형식과 C 화면 API 합의 → (4) 통합 계약 테스트.

합의되면 이 문서와 [API_SPEC.md](API_SPEC.md), Pydantic 모델, Java DTO, Mock/통합 계약 테스트를 **같은 변경 작업에서 갱신**한다. 아직 합의되지 않은 예시 필드를 확정 계약으로 표시하지 않는다.
