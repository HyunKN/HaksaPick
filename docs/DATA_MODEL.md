# HaksaPick B 파트 데이터 구조 v0.1

> 상태: **도메인 의미/보호 규칙은 합의됨, 실제 테이블·컬럼·타입은 제안 또는 미결정**
> 관련: [PRD](PRD.md) · [API_SPEC](API_SPEC.md) · [개발 프로세스](DEVELOPMENT_PROCESS.md)
> 본 문서는 **B 파트가 필요로 하는 논리 데이터 구조**다. A/DB 파트의 실제 수집 테이블·ERD를 대신하거나 변경하지 않는다.

## 1. 범위와 결정 상태

| 도메인 객체 | 왜 필요한가 | 확정된 개념 | 아직 미확정인 것 |
|---|---|---|---|
| 사용자 기본 프로필 | 개인 조건의 기준 | 학과·학년·재학 상태 등 고정 정보는 폼 중심 관리 | 필수/선택 필드, 코드표, DB 컬럼 |
| 확정 관심 설정 | 추천의 기준 | 사용자 승인 후에만 변경, 신뢰 가능한 원본은 DB | 실제 저장 형식·테이블 |
| 사용자 정의 조건 | 키워드 외 자연어 조건 | 개별 ID로 추가·수정·삭제; 포함/제외 및 적용 범위 구분 | 조건 표현식/타입/상한 |
| 승인 대기 변경안 | LLM 출력과 확정 데이터 분리 | 제안·승인·취소를 별도로 관리 | 상태 값, 만료/버전 저장 형태 |
| 대화 컨텍스트 | 앞 대화의 뜻을 유지 | 최근 대화/미해결 질문/요약과 확정 설정은 구분 | 보존 기간·Compaction 임계값 |
| 공지 원본(A 제공) | 의미 분석·추천 근거 | 식별자·원문·출처·갱신 정보 필요 | A 파트의 실제 스키마와 제공 범위 |
| 공지 분석 결과 | 공통 특징 재사용 | 공지 ID와 버전 기준으로 추출 결과 재사용 검토 | 저장 주체·테이블·재처리 정책 |
| 사용자별 추천·피드백 | 추천 개선 | 관련성/자격 구분, 도움/무관·저장/제외 등 반응 | 기록 방식·기한·스코어 |

## 2. 핵심 논리 구조 (초안)

```text
AuthenticatedUser (Backend가 인증)
  ├── ConfirmedPreferenceState (사용자별 승인된 설정 + version)
  │     ├── AcademicProfile (학적 기본 필드)
  │     └── CustomCondition[] (안정적인 ID를 갖는 추가 조건)
  ├── PendingPreferenceProposal[] (승인 전 변경안)
  ├── ConversationContext (최근 메시지 / 요약 / 미해결 질문)
  └── UserRecommendationFeedback[] (사용자별 반응)

Notice (A/DB의 원본, 권위 있는 출처)
  └── NoticeSemanticAnalysis (notice ID + 원본 version 기반, 제안)
       └── PersonalizedRecommendation (사용자 설정과 대조한 판단)
```

관계도는 **도메인 간 논리 연결**이며 실제 FK/ERD나 저장소 구성을 확정한 것이 아니다.

## 3. 확정 설정과 추가 조건

**확정된 정책:**
- 사용자별 확정 설정에는 **버전**이 있어야 하고, 동시 변경 시 버전 충돌을 처리한다.
- 관심 조건은 단순 키워드뿐 아니라 사용자 정의 문장·포함·제외·선호·필수 여부를 표현할 수 있어야 한다.
- 확정 설정의 출처는 Backend가 관리하는 **승인된 DB 상태**이며, 대화 요약을 진실의 원본으로 삼지 않는다.
- 변경안은 `add`, `update`, `remove` 형태를 다룰 수 있어야 하며, 확정 적용은 승인 후 Backend에서만 수행한다.

**논리적 JSON 예시 — 제안이며 확정 필드명 아님:**

```json
{
  "preference_version": 3,
  "academic_profile": {
    "department": "예시학과",
    "year": 4,
    "enrollment_status": "enrolled"
  },
  "conditions": [
    {
      "condition_id": "cond-001",
      "scope": "notices",
      "polarity": "include",
      "strength": "required",
      "text": "현장실습과 관련된 모집 공지"
    },
    {
      "condition_id": "cond-002",
      "scope": "notices",
      "polarity": "exclude",
      "strength": "required",
      "text": "국가장학금"
    }
  ]
}
```

`strength` 값, `scope`/학교·학적 enum, version 타입, null/필수 여부는 실제 구현 시 확정할 **제안**이다.

**권장 저장 전략(제안):** 고정 학적 필드와 개별 사용자 조건을 구분해 저장하고, 유연한 세부 내용은 JSON 필드 등을 활용한다. 사용자가 새 조건을 말할 때마다 DB 컬럼을 만드는 방식은 사용하지 않는다. 최종 테이블명·JSONB 사용 여부·FK/인덱스는 DB 담당과 협의한다.

## 4. 승인 대기 변경안과 동시성

변경안은 확정 설정과 섞지 않고 구분한다.

```json
{
  "proposal_id": "proposal-001",
  "base_preference_version": 3,
  "status": "pending",
  "operations": [
    {
      "operation": "remove",
      "target_condition_id": "cond-001"
    }
  ]
}
```

**강제 규칙:** Backend가 승인 제안의 소유권, 제시 당시 원본 내용, 현재 설정 버전, 승인 여부를 검증한다. 적용은 원자적이어야 하고 중복 승인은 재적용하지 않는다. 제안 ID 및 조건 ID를 LLM 임의 출력대로 신뢰하지 않는다. 위 `status` 값과 필드는 저장 구조가 아닌 **예시**다.

## 5. 대화 데이터와 컨텍스트

| 정보 | 역할 | 주의 |
|---|---|---|
| 최근 메시지 | 이번 턴의 의미·지시 대상 파악 | 필요 분량만 Core로 전송 |
| 미해결 질문/대기 변경안 | 다음 턴에서 이어서 처리 | 대화 요약에 묻히지 않게 분리 |
| 과거 대화 요약 | 오래된 맥락 압축 | **확정 조건의 원본이 될 수 없음** |
| 확정 사용자 설정 | 모델 판단의 확실한 기준 | 매 요청에서 승인된 원본 DB 값 사용 |

원문 대화 보관, 최소 저장, 로그 마스킹, 삭제/철회 정책은 **실제 사용자 정보를 저장하기 전에 결정**한다.

## 6. A 파트에서 받아야 하는 공지 데이터

**B 파트의 최소 의미 요구**(A 파트 컬럼 요구가 아님): 식별자, 제목, 본문, 출처 URL, 게시 시점, 갱신/버전 식별 방법. 없는 필드는 없는 것으로 표시하며 AI가 만들어내지 않는다.

```json
{
  "notice_id": "example-notice-001",
  "title": "예시 공지",
  "content": "가상의 공지 본문",
  "source_url": "https://example.edu/notice/001",
  "published_at": "2026-11-18",
  "version": "1"
}
```

이 JSON은 **B 파트의 Mock 입력 예시**일 뿐이다. 수집 사이트/DB의 실제 컬럼 구조, 필수·선택 필드, 공지 본문 추출·첨부 지원·중복/수정 감지·실행 주기는 A/DB 파트 확정이 필요하다. 크롤러 구현이나 접근 정책을 이 문서에서 지시하지 않는다.

## 7. 공통 공지 분석과 개인화 추천의 차이

- **공지 공통 분석:** 공지 원문에서 주제, 신청 대상, 기한, 행동, 원문 근거 등을 추출. 가능하면 공지 ID+버전 단위로 재사용.
- **개인화 추천:** 같은 공지라도 사용자별 확정 설정과 비교하여 관심 관련성(`relevance`)과 실제 지원 자격(`eligibility`)을 구분해 판단.
- **근거 관리:** 추천 사유는 실제 수집된 원문과 연결하고, 원문에 없는 자격/마감일을 추정해 확정 표시하지 않는다.
- **피드백:** 저장·제외·도움·무관 등의 사용자 반응은 평가·향후 개선에 사용할 수 있으나, 피드백이 자동으로 확정 조건을 수정하지는 않는다.

점수 산출 방식, 공통 분석 결과 저장, 개인별 캐시와 알림 정책은 팀 연동 전에는 미결정이다.

## 8. 실제 구현 전에 합의할 질문 (필수만)

2. **A/DB:** 공지 ID·원문·게시일·갱신 정보·첨부 등 실제로 제공 가능한 필드와 누락 시 표현은?
3. **B/C:** 추천 카드가 요구하는 근거·관련성·자격 불명확 상태·피드백 표현은?
4. **공통:** 사용자 데이터 보존/삭제·조건 최대 개수·최종 API/오류 응답 계약은?
