# HaksaPick PRD v0.1 — AI 개인화·학사 공지 추천

- 상태: **기준선(Baseline)**, 2026-11-18
- 범위: 제품 전체 흐름을 간략히 정의하되, **B 파트(AI 개인화·추천)**를 중심으로 기록
- 원칙: 이 문서의 **확정 / 제안 / 미결정**을 혼동하지 않는다. 문서를 고정 기준으로 사용하고 변경은 별도 논의와 PR로 반영한다.
- 구현 상태: 아래 기능은 **요구사항 및 설계**이며, 작동·평가 완료를 의미하지 않는다.

## 1. 문제와 목표

학사 공지 게시판이 분산되어 있고, 학생마다 필요한 공지·자격·제외 조건이 다르다. 사용자가 매번 여러 게시판을 확인하고 검색어를 조합하는 부담을 줄인다.

**목표:** 사용자가 기본 정보와 자연어 대화를 통해 개인 관심 조건을 정의·확정·수정할 수 있고, 수집된 공지 중 자신과 관련 있는 항목을 **근거와 함께** 확인하는 PC 웹서비스.

**성공 기준(초기):**
- 사용자가 관심 조건을 검토·승인한 경우에만 확정 설정이 변경된다.
- 추천에는 원문 출처와 관련 이유를 표시하며, 지원 자격이 불명확하면 불명확하다고 표시한다.
- 같은 입력과 동일한 데이터로 기본 기능을 재현·테스트할 수 있다.
- 추천 품질과 입력 토큰·호출 횟수·지연시간을 측정하고 개선 전후를 비교할 수 있다.

## 2. 사용자 흐름 (확정 방향)

1. 사용자는 PC 웹에서 로그인한다.
2. 학교·학과·학년·재학 상태 등 **기본 학적 정보는 폼**으로 입력하거나 수정한다. 모르는 항목은 강요하지 않는다.
3. 사용자는 **Claude Haiku 기반 채팅**으로 원하는 공지, 포함·제외·추가 조건을 자연어로 설명한다.
4. 시스템은 기존 확정 설정과 필요한 대화 맥락을 고려해 **추가 질문 또는 설정 변경안**을 제시한다.
5. 사용자가 변경안을 검토·수정·승인하면 Backend가 검증 후 저장한다. 단순 발언을 자동 저장하지 않는다.
6. 정기 실행·웹 로그인·수동 요청을 계기로 수집된 공지를 개인 설정에 따라 분석하고 추천한다. 실행 트리거의 구현 책임은 팀 간 협의한다.
7. 웹에서 추천 이유·원문 링크·기한·불확실성 등을 확인하고, 확인/저장/제외·도움 여부를 피드백할 수 있다.

**범위 제외:** Windows 네이티브 팝업·OS 로그인 자동 실행, 모바일 앱, 무단 사이트 크롤링, 모델 자체 학습 및 필수 벡터 DB 구축.

## 3. 담당 경계

| 영역 | 주 업무 | B 파트 연동점 |
|---|---|---|
| A — 데이터 수집·관리 | 허용된 학사 공지 수집, 원문·URL·게시일·갱신 정보 제공 | 공지 ID·버전·원문·출처 전달 |
| **B — AI 개인화·추천** | 대화/조건 추출, 변경안, 공지 의미 분석, 관련성·자격 판단, 평가 | 본 PRD의 주요 구현 범위 |
| C — 웹·알림 | 폼·채팅·설정 승인 UI, 추천 목록·웹 알림·피드백 UI | 요청/응답 및 화면 동작 협의 |
| 공통 Backend | 인증·권한·DB 쓰기·Core 호출·실행 제어 | 담당자는 팀 내 별도 확정 |

A의 수집 가능 게시판과 자료의 최신성은 **입력 전제 조건**이다. B는 실제 제공된 데이터를 기준으로 동작하며, 수집되지 않은 공지를 수집된 것처럼 추천하지 않는다.

## 4. 기술 구성 (합의 방향)

```text
Frontend (React 18 / TypeScript / Vite)
    → /api
Backend (Java 17 / Spring Boot 3.3.10 / Gradle)
    → 내부 HTTP
Core (Python 3.11 / FastAPI / Pydantic v2 / Poetry)
    → Anthropic Claude API (Haiku)
```

- Frontend는 Core·Claude를 직접 호출하지 않는다.
- 인증이 필요한 Frontend→Backend API는 JWT Bearer 전제.
- Backend는 인증, 사용자 식별, 설정 조회·승인 저장, 권한·버전 검사 담당.
- Core는 LLM 입력 구성, Claude 호출, 구조화 결과 검증, 추천 판단 담당.
- **Claude는 DB에 직접 쓰지 않는다.** LLM 출력은 신뢰하지 않는 제안 데이터로 취급한다.
- Claude의 구체적 Haiku 모델 ID는 검증된 지원 모델 중 설정값으로 지정한다.
- UTF-8 사용, 비밀값·환경변수 실값·개인정보 샘플 커밋 금지.

## 5. B 파트 주요 기능

### P0 — 대화형 개인 설정

- 사용자 메시지의 **의도** 구분: 대화/질문, 정보 제공, 조건 추가·수정·삭제, 피드백.
- 기존 **확정된 설정 + 최근 관련 대화 + 미확정 변경안**을 이용해 의미를 해석.
- 필요할 때만 추가 질문하고 이미 알려 준 사실을 반복 질문하지 않는다.
- 기본 설정 예: 학적 정보, 관심 분야, 목적, 포함/제외 기준, 우선순위.
- 사용자 정의 조건은 스키마를 사용자 대화마다 변경하지 않고 **안정된 DB 구조 아래 개별 ID로 추가·수정·삭제**할 수 있게 설계한다.
- 사용자 정의 조건은 적용 범위(scope), 필수/선호 여부, 설명, 검증 상태를 구분할 수 있어야 한다.
- 변경은 **추가(add) / 수정(update) / 제거(remove) 제안**으로 표현하며, 사용자 승인 전에는 확정 설정을 변경하지 않는다.

### P1 — 공지 분석 및 추천

- 공지에서 관련 주제, 지원 대상, 필요 행동, 기간/마감, 원문 근거를 추출한다.
- 관련성(relevance)과 신청 자격(eligibility)을 **분리**해 판단한다. 자격 미확인은 '불명확'으로 표시한다.
- 개인 설정의 필수 조건과 선호 조건을 구분해 추천한다.
- 공통 공지 분석은 **공지 ID/버전 단위로 재사용**할 수 있도록 설계한다.
- 추천 후보 검색은 초기엔 **메타데이터 필터/키워드 기준선**으로 시작한다. BM25·동의어·의미 검색·Hybrid·RAG/지식그래프는 평가 후 필요할 때 추가한다.
- 추천 결과는 출처·추천 이유·사용자 확인/제외 기록을 활용한다. 추천 결과 전체의 영구 캐시 여부는 미결정이다.

### P1 — Context Engineering·비용·평가

- Claude API 호출은 서버 측에서 대화 맥락을 명시적으로 구성한다.
- **확정 개인 설정은 정확한 DB 원본이 기준**이다. 대화 요약(Compaction)으로 이를 대체하지 않는다.
- 최근 대화·미해결 질문·승인 대기 변경안은 별도 상태로 유지하고, 오래된 대화만 필요 시 압축한다.
- 모든 사용자 조건/전체 공지/전체 대화를 매번 LLM에 넣지 않는다. 관련 후보를 선별하되 중요한 조건 누락을 평가한다.
- 토큰 수·요청 횟수·지연·오류와 추출/추천 품질을 비교·기록한다.
- 프롬프트 인젝션을 문자열 필터만으로 완벽하게 차단할 수 있다고 가정하지 않는다. 입력 제한과 **권한 분리, 검증, 허용된 작업만 실행**을 결합한다.

## 6. 최소 데이터·API 계약 (초안, 미확정)

**개념적 데이터:** 사용자 기본 학적 정보, 관심사, 개별 추가 조건(ID·범위·내용·상태), 확정 설정 버전, 대화 문맥, 승인 대기 변경안, 공지 ID·원문·버전·출처, 사용자별 추천/피드백.

**Core 입력 (개념):** `message`, `confirmed_preferences`, `recent_history`, `pending_change`, `preference_version` (필요한 필드만 전송).

**Core 출력 (개념):** `assistant_message`, `decision` (ask/propose/no_change), `proposed_changes` (add/update/remove), 관련 판단 근거 및 오류 상태.

**데이터 저장 흐름:** React → Backend → Core → Claude → Core(출력 검증) → Backend → React(변경안 확인) → Backend(인증·소유권·버전 검사) → DB.

- API 경로, DB 테이블, Pydantic 모델의 **최종 필드·응답 래퍼는 팀 연동 전 확정**한다.
- 조건 ID는 Backend가 제공·검증하며, Claude가 임의로 생성한 기존 ID를 신뢰하지 않는다.
- 서로 다른 세션이 같은 설정을 수정할 경우 **버전 기반 낙관적 동시성 제어**를 고려한다.
- 과도한 조건 증가에는 개수/길이 상한, 중복/모순 검사, 관련 조건만 LLM 전달하는 정책을 검토한다. 수치는 평가 후 결정한다.

## 7. 구현 전략 — 복잡도 최소화

**기본 구현:** FastAPI + Anthropic SDK + Pydantic + Spring Boot API. 우선 사용자 조건 추출·승인 저장까지 연결한다.

**교체 가능 구조:** Core의 외부 LLM 호출과 대화 처리 흐름에 작은 인터페이스 경계를 둔다. 필요하면 Claude SDK ↔ LangChain, 일반 Python ↔ LangGraph를 교체·비교할 수 있도록 한다. **LangChain/LangGraph 도입은 확정 요구사항이 아니다.** 추가 의존성 허용 여부도 검토한다.

**우선 개발 순서:**
1. 설정 스키마·Core 입력/출력 계약 최소안 확정
2. Mock 기반 대화/변경안/승인 저장 E2E 테스트
3. 실제 Claude Haiku 연동과 추출 평가
4. 공지 샘플 기반 관련성 추천 기준선 및 평가
5. 비용 최적화·검색/Compaction/프레임워크 비교 실험

## 8. 검증 기준

- **조건 추출:** 추가/수정/삭제, 모호한 발언, 단순 대화, 이전 조건 유지, 제외 조건 유지, 악성 입력 테스트.
- **승인·보안:** 승인 전 DB 불변, 타인 조건 변경 불가, 오래된 버전의 갱신 거절, 반복 승인 시 이중 반영 방지.
- **공지 추천:** 관련 공지 누락률(Recall), 관련성/자격 판단 오류, 원문 근거 유무, 데이터 최신성·미확인 표시.
- **비용/안정성:** 입력/출력 토큰, LLM 호출 수, 시간, 오류율. Mock 테스트는 실키 없이 재현.
- **회귀:** 수정 전/후 동일 평가셋 비교. 실제 측정값이 없으면 PASS나 개선 수치를 주장하지 않는다.

## 9. 미결정 사항

1. 사용자 설정·개별 추가 조건의 최종 DB 스키마와 상한/정리 정책
2. 대화 기록 보존 기간, Compaction 임계값과 맥락 품질 기준
3. Core ↔ Backend 최종 JSON·API 경로·공통 응답 형태
4. 공지 검색 인덱스/메타데이터 책임, 공통 분석 결과의 저장 위치
5. 개인별 추천 트리거 및 결과 재사용/알림 중복 방지 정책
6. Claude 모델 버전 고정 및 SDK 외 추가 프레임워크 채택 여부

## 10. 이 PRD를 기준으로 개발하는 규칙

- **이 문서가 제품 요구사항의 기준선**이다. 다른 채팅의 추정이나 과거 계획보다 최신 승인된 PRD를 우선한다.
- 확정되지 않은 항목을 임의 확정하지 않는다. 개발에 필요하면 작게 선택하고 결과를 명시한다.
- PRD 변경은 이유, 검증 근거, 영향 범위를 남겨 **PR로 검토한 뒤 반영**한다.
- 구현·성능·진행률은 코드·테스트 기록 없이 완료로 표시하지 않는다.
- 외부로 공개할 수 없는 제공 가이드·샘플 원본, 비밀키, 실제 사용자 정보는 저장소에 올리지 않는다.
