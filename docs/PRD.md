# HaksaPick PRD v0.2 — AI 개인화·학사 공지 추천

- 상태: **기준선(Baseline) 수정안**, 2026-11-18
- 변경: 필수 준수 원칙·기술 선정 이유·LangChain/LangGraph 도입과 롤백 전략 명확화
- 범위: 제품 전체 흐름을 간략히 정의하되, **B 파트(AI 개인화·추천)**를 중심으로 기록
- 원칙: 이 문서의 **확정 / 제안 / 미결정**을 혼동하지 않는다. 문서를 고정 기준으로 사용하고 변경은 별도 논의와 PR로 반영한다.
- 구현 상태: 아래 기능은 **요구사항 및 설계**이며, 작동·평가 완료를 의미하지 않는다.

## 1. 문제와 목표

학사 공지 게시판이 분산되어 있고, 학생마다 필요한 공지·자격·제외 조건이 다르다. 사용자가 매번 여러 게시판을 확인하고 검색어를 조합하는 부담을 줄인다.

**목표:** 사용자가 기본 정보와 자연어 대화를 통해 개인 관심 조건을 정의·확정·수정할 수 있고, 수집된 공지 중 자신과 관련 있는 항목을 **근거와 함께** 확인하는 PC 웹서비스.

**성공 기준(초기):**
- 사용자가 관심 조건을 검토·승인한 경우에만 확정 설정이 변경된다.
- 추천에는 원문 출처와 관련 이유를 표시하며, 지원 자격이 불명확하면 불명확하다고 표시한다.
- 같은 입력과 동일한 데이터로 기본 기능을 재현·테스트할 수 있다.
- 추천 품질과 입력 토큰·호출 횟수·지연시간을 측정하고 개선 전후를 비교할 수 있다.

## 2. 사용자 흐름 (확정 방향)

1. 사용자는 PC 웹에서 로그인한다.
2. 학교·학과·학년·재학 상태 등 **기본 학적 정보는 폼**으로 입력하거나 수정한다. 모르는 항목은 강요하지 않는다.
3. 사용자는 **Claude Haiku 기반 채팅**으로 원하는 공지, 포함·제외·추가 조건을 자연어로 설명한다.
4. 시스템은 기존 확정 설정과 필요한 대화 맥락을 고려해 **추가 질문 또는 설정 변경안**을 제시한다.
5. 사용자가 변경안을 검토·수정·승인하면 Backend가 검증 후 저장한다. 단순 발언을 자동 저장하지 않는다.
6. 정기 실행·웹 로그인·수동 요청을 계기로 수집된 공지를 개인 설정에 따라 분석하고 추천한다. 실행 트리거의 구현 책임은 팀 간 협의한다.
7. 웹에서 추천 이유·원문 링크·기한·불확실성 등을 확인하고, 확인/저장/제외·도움 여부를 피드백할 수 있다.

**범위 제외:** Windows 네이티브 팝업·OS 로그인 자동 실행, 모바일 앱, 무단 사이트 크롤링, 모델 자체 학습 및 필수 벡터 DB 구축.

## 3. 담당 경계

| 영역 | 주 업무 | B 파트 연동점 |
|---|---|---|
| A — 데이터 수집·관리 | 허용된 학사 공지 수집, 원문·URL·게시일·갱신 정보 제공 | 공지 ID·버전·원문·출처 전달 |
| **B — AI 개인화·추천** | 대화/조건 추출, 변경안, 공지 의미 분석, 관련성·자격 판단, 평가 | 본 PRD의 주요 구현 범위 |
| C — 웹·알림 | 폼·채팅·설정 승인 UI, 추천 목록·웹 알림·피드백 UI | 요청/응답 및 화면 동작 협의 |
| 공통 Backend | 인증·권한·DB 쓰기·Core 호출·실행 제어 | 담당자는 팀 내 별도 확정 |

A의 수집 가능 게시판과 자료의 최신성은 **입력 전제 조건**이다. B는 실제 제공된 데이터를 기준으로 동작하며, 수집되지 않은 공지를 수집된 것처럼 추천하지 않는다.

## 4. 기술 구성 (합의 방향)

```text
Frontend (React 18 / TypeScript / Vite)
    → /api
Backend (Java 17 / Spring Boot 3.3.10 / Gradle)
    → 내부 HTTP
Core (Python 3.11 / FastAPI / Pydantic v2 / Poetry)
    → Anthropic Claude API (Haiku)
```

- Frontend는 Core·Claude를 직접 호출하지 않는다.
- 인증이 필요한 Frontend→Backend API는 JWT Bearer 전제.
- Backend는 인증, 사용자 식별, 설정 조회·승인 저장, 권한·버전 검사 담당.
- Core는 LLM 입력 구성, Claude 호출, 구조화 결과 검증, 추천 판단 담당.
- **Claude는 DB에 직접 쓰지 않는다.** LLM 출력은 신뢰하지 않는 제안 데이터로 취급한다.
- Claude의 구체적 Haiku 모델 ID는 검증된 지원 모델 중 설정값으로 지정한다.
- UTF-8 사용, 비밀값·환경변수 실값·개인정보 샘플 커밋 금지.

### 기술 선정 이유 (확정·실험 구분)

| 기술 | 채택/적용 상태 | 왜 사용하는가 | 대안·주의 |
|---|---|---|---|
| React 18 / TypeScript / Vite 6 | 팀 기술 기준 | PC 웹 컴포넌트 개발·정적 타입·빠른 개발/빌드 | AI 코어가 브라우저에서 직접 호출되지 않음 |
| Java 17 / Spring Boot 3.3.10 / Gradle | 팀 기술 기준 | JWT 인증, 사용자별 권한, API, DB 트랜잭션, Core 호출 관리 | 비즈니스 상태 저장의 최종 책임은 Backend |
| Python 3.11 / FastAPI | Core 기준 | 모델·검색·데이터 처리를 HTTP 서비스로 노출 | Backend와 계약된 JSON만 교환 |
| Pydantic v2 | Core 기준 | 요청·응답과 LLM 출력의 구조 및 타입 검증 | 검증 통과가 내용의 사실성까지 보장하지는 않음 |
| Poetry | Core 기준 | 의존성 고정, 재현 가능한 설치/빌드 | Lock 파일 및 호환성 확인 필요 |
| Anthropic Claude Haiku API | **사용 결정** | 자연어 조건 이해, 추가 질문, 공지 의미 분석 | 실제 모델 ID·가격·지원 기능은 개발 시 검증 후 설정으로 고정 |
| **LangChain** | **B 파트 도입 결정** | Claude 연동, 구조화 출력, 도구/검색 인터페이스를 통일하고 교체·비교 용이하게 함 | 단일 SDK 호출보다 복잡해질 수 있어 효과를 실측; Claude SDK 직접 호출 대체 경로 유지 |
| **LangGraph** | **B 파트 도입 결정** | 대화/추천의 다단계 실행, 상태·분기·반복 및 추후 중단·재개를 명시적으로 관리 | 단순 승인 API에 과잉 사용하지 않음; 기본 Python 워크플로우 대체 경로 유지 |
| 메타데이터 필터 / 키워드 기준선 | 초기 구현 대상 | 불필요한 LLM 후보를 줄이고 누락을 평가할 비교 기준 확보 | BM25/동의어/벡터·Hybrid 검색은 실험 후 선택 |
| LangSmith / 별도 지식그래프 / 벡터 DB | **도입 미확정** | 추적·평가 또는 복잡한 탐색 요구가 실제 발생했을 때만 검토 | 외부 서비스·새 데이터 저장소를 기본 전제로 삼지 않음 |

**선정 판단 원칙:** 프레임워크 자체를 도입 성과로 보지 않는다. 동일 조건으로 정확도, 코드 수정 범위, 비용·지연시간, 오류 복구 성능을 측정한다. 추가 외부 의존성의 배포 허용 여부는 적용 전에 팀·검증 담당자와 확인한다.

## 5. B 파트 주요 기능

### P0 — 대화형 개인 설정

- 사용자 메시지의 **의도** 구분: 대화/질문, 정보 제공, 조건 추가·수정·삭제, 피드백.
- 기존 **확정된 설정 + 최근 관련 대화 + 미확정 변경안**을 이용해 의미를 해석.
- 필요할 때만 추가 질문하고 이미 알려 준 사실을 반복 질문하지 않는다.
- 기본 설정 예: 학적 정보, 관심 분야, 목적, 포함/제외 기준, 우선순위.
- 사용자 정의 조건은 스키마를 사용자 대화마다 변경하지 않고 **안정된 DB 구조 아래 개별 ID로 추가·수정·삭제**할 수 있게 설계한다.
- 사용자 정의 조건은 적용 범위(scope), 필수/선호 여부, 설명, 검증 상태를 구분할 수 있어야 한다.
- 변경은 **추가(add) / 수정(update) / 제거(remove) 제안**으로 표현하며, 사용자 승인 전에는 확정 설정을 변경하지 않는다.

### P1 — 공지 분석 및 추천

- 공지에서 관련 주제, 지원 대상, 필요 행동, 기간/마감, 원문 근거를 추출한다.
- 관련성(relevance)과 신청 자격(eligibility)을 **분리**해 판단한다. 자격 미확인은 '불명확'으로 표시한다.
- 개인 설정의 필수 조건과 선호 조건을 구분해 추천한다.
- 공통 공지 분석은 **공지 ID/버전 단위로 재사용**할 수 있도록 설계한다.
- 추천 후보 검색은 초기엔 **메타데이터 필터/키워드 기준선**으로 시작한다. BM25·동의어·의미 검색·Hybrid·RAG/지식그래프는 평가 후 필요할 때 추가한다.
- 추천 결과는 출처·추천 이유·사용자 확인/제외 기록을 활용한다. 추천 결과 전체의 영구 캐시 여부는 미결정이다.

### P1 — Context Engineering·비용·평가

- Claude API 호출은 서버 측에서 대화 맥락을 명시적으로 구성한다.
- **확정 개인 설정은 정확한 DB 원본이 기준**이다. 대화 요약(Compaction)으로 이를 대체하지 않는다.
- 최근 대화·미해결 질문·승인 대기 변경안은 별도 상태로 유지하고, 오래된 대화만 필요 시 압축한다.
- 모든 사용자 조건/전체 공지/전체 대화를 매번 LLM에 넣지 않는다. 관련 후보를 선별하되 중요한 조건 누락을 평가한다.
- 토큰 수·요청 횟수·지연·오류와 추출/추천 품질을 비교·기록한다.
- 프롬프트 인젝션을 문자열 필터만으로 완벽하게 차단할 수 있다고 가정하지 않는다. 입력 제한과 **권한 분리, 검증, 허용된 작업만 실행**을 결합한다.

## 6. 최소 데이터·API 계약 (초안, 미확정)

**개념적 데이터:** 사용자 기본 학적 정보, 관심사, 개별 추가 조건(ID·범위·내용·상태), 확정 설정 버전, 대화 문맥, 승인 대기 변경안, 공지 ID·원문·버전·출처, 사용자별 추천/피드백.

**Core 입력 (개념):** `message`, `confirmed_preferences`, `recent_history`, `pending_change`, `preference_version` (필요한 필드만 전송).

**Core 출력 (개념):** `assistant_message`, `decision` (ask/propose/no_change), `proposed_changes` (add/update/remove), 관련 판단 근거 및 오류 상태.

**데이터 저장 흐름:** React → Backend → Core → Claude → Core(출력 검증) → Backend → React(변경안 확인) → Backend(인증·소유권·버전 검사) → DB.

- API 경로, DB 테이블, Pydantic 모델의 **최종 필드·응답 래퍼는 팀 연동 전 확정**한다.
- 조건 ID는 Backend가 제공·검증하며, Claude가 임의로 생성한 기존 ID를 신뢰하지 않는다.
- 서로 다른 세션이 같은 설정을 수정할 경우 **버전 기반 낙관적 동시성 제어**를 고려한다.
- 과도한 조건 증가에는 개수/길이 상한, 중복/모순 검사, 관련 조건만 LLM 전달하는 정책을 검토한다. 수치는 평가 후 결정한다.

## 7. 구현 전략 — 실제 도입 + 빠른 되돌리기

**기본 구현 결정:** B 파트 Core는 **FastAPI + Pydantic v2 + LangChain(Claude 연동) + LangGraph(대화/추천 실행 흐름)**을 도입한다. Anthropic SDK는 LangChain 어댑터 내부에서 사용될 수 있으며, 프레임워크 없이 직접 호출하는 대체 구현도 마련해 둔다. 단, 모든 기능을 처음부터 에이전트로 만들지는 않는다.

**전환 경계는 두 가지로 제한한다:**
- `LLMAdapter`: LangChain 연동(기본) ↔ Claude SDK 직접 호출(대체). 동일한 도메인 입출력 스키마를 반환한다.
- `WorkflowRunner`: LangGraph(기본) ↔ 순수 Python 기본 흐름(대체). API·DB에는 프레임워크 내부 State 객체를 노출하지 않는다.

**전환 예시 설정:** `LLM_ADAPTER=langchain|anthropic_sdk`, `WORKFLOW_ENGINE=langgraph|basic`. 실제 설정명은 구현 시 확정하고 테스트한다. **설정값만으로 무조건 전환된다고 가정하지 않는다**: 각 구현, 의존성, 동일 계약, 예외 처리, 회귀 테스트가 준비돼야 한다.

- Core의 HTTP API, Pydantic 도메인 스키마, 사용자 설정 저장 방식은 전환 전후 동일하게 유지한다.
- LangGraph 체크포인트는 복잡한 중단/재개가 실제 필요한 경우에만 영속 저장소로 구현한다. 테스트용 메모리 체크포인트를 운영 안정성으로 주장하지 않는다.
- **승인 대기 및 DB 저장은 Backend의 명시적 상태와 트랜잭션으로 관리**한다. LangGraph에서 재개되더라도 승인·권한·버전 검사는 Backend가 다시 수행한다.
- 모델·워크플로우 전환 시 설정 추출 정확도, 비용, 호출 횟수, 예외/재시도, 상태 복원 테스트를 공통 평가 데이터로 실행한다.
- 한 번의 호출만 필요한 단계는 단일 Node로 유지하며 불필요한 다중 에이전트·도구 호출 루프를 만들지 않는다.

**우선 개발 순서:**
1. 설정 스키마·Core 입출력 계약 최소안 및 필수 보안 조건 확정
2. LangChain/Claude 호출 어댑터 + LangGraph 최소 대화 흐름 구현, Mock 테스트
3. SDK·순수 Python 대체 경로 구성 및 교체 회귀 테스트
4. Backend 승인 저장 E2E, 실제 Claude 추출 평가
5. 공지 샘플 추천 기준선·품질/비용 평가; 필요 시 검색·Compaction 확장

## 8. 검증 기준

- **조건 추출:** 추가/수정/삭제, 모호한 발언, 단순 대화, 이전 조건 유지, 제외 조건 유지, 악성 입력 테스트.
- **승인·보안:** 승인 전 DB 불변, 타인 조건 변경 불가, 오래된 버전의 갱신 거절, 반복 승인 시 이중 반영 방지.
- **공지 추천:** 관련 공지 누락률(Recall), 관련성/자격 판단 오류, 원문 근거 유무, 데이터 최신성·미확인 표시.
- **비용/안정성:** 입력/출력 토큰, LLM 호출 수, 시간, 오류율. Mock 테스트는 실키 없이 재현.
- **회귀:** 수정 전/후 동일 평가셋 비교. 실제 측정값이 없으면 PASS나 개선 수치를 주장하지 않는다.

## 9. 반드시 지킬 안전·품질 원칙

다음은 구현 세부 선택과 관계없이 **MUST(필수)**로 준수한다. 아직 정하지 않은 수치·보존 기간은 미결정으로 남기되, 그 미결정 상태를 운영 허가로 해석하지 않는다.

1. **확정 설정 보호:** LLM은 기존 설정을 자동 수정/삭제하지 않는다. 생성하는 것은 변경 제안이며, 승인 전 DB의 확정 상태는 불변이다. 변경 제안과 사용자 승인 내용은 일치해야 한다.
2. **인증·권한·버전·중복 방지:** 사용자 식별은 Backend 인증 정보에 의존한다. 클라이언트/LLM이 전달한 user ID·condition ID를 무조건 신뢰하지 않는다. 승인 시 해당 사용자 소유권과 설정 버전을 검증하고 원자적으로 반영한다. 같은 승인을 반복해도 이중 변경하지 않는다.
3. **신뢰 경계:** 사용자 채팅, 크롤링 공지 원문, 검색 결과, Tool 출력, Claude 응답을 시스템 지시나 권한 상승 명령으로 취급하지 않는다. 도구와 DB 작업은 서버에서 허용 목록·입력 스키마·권한 검사를 거친다. '문자열 차단 필터만으로 안전'이라고 간주하지 않는다.
4. **오류 안전성:** Claude API 타임아웃·실패, 잘못된 JSON, Pydantic 검증 실패, 검색 실패가 발생해도 기존 확정 설정이 손상되지 않는다. 타임아웃·재시도·중복 실행 제한을 둔다. 실패를 성공 응답으로 위장하지 않는다.
5. **개인정보 최소화:** 저장·전송·로그에는 필요한 사용자 정보만 포함한다. 사용자 간 설정·대화 유출을 방지한다. 원문 대화/요약의 보존 기간·삭제/철회 처리·접근 정책은 실제 사용자 데이터 저장 전에 확정한다. 로그에 API 키나 대화 전문을 무심코 남기지 않는다.
6. **컨텍스트 정확성:** Compaction으로 확정 조건, 제외 조건, 승인 대기 변경안을 대체하거나 소실하지 않는다. 관련성 검색으로 컨텍스트를 줄일 때 필수 조건·강한 제외 조건이 빠지는 오류를 평가한다.
7. **추천 근거·불확실성:** 공지 출처 URL/문서 ID·버전을 추적하고 원문에 없는 자격·혜택·마감일을 단정하지 않는다. 지원 자격과 관심 관련성을 분리하며, 미확인 사항은 '불명확'으로 표시한다.
8. **비용 및 무한 실행 방지:** LLM 사용량, 최대 입력 크기, 허용 호출·재시도 횟수, 도구 실행 제한을 둔다. 정확한 한도 수치는 테스트 후 정한다.
9. **비밀·의존성 관리:** 실제 키·토큰·개인정보·내부 가이드/샘플을 저장소에 커밋하지 않는다. Python 의존성과 버전을 관리하고, 별도 설치 없이 실행 가능한 척하지 않는다. 추가 패키지는 적용 환경과의 호환성을 확인한다.
10. **검증 없는 완료 금지:** 주요 기능은 성공/경계/실패/악성 입력 테스트를 통과하고 재현 가능한 테스트 기록이 있어야 완료로 표시한다. 측정하지 않은 정확도·비용 절감·성능 수치를 주장하지 않는다.

### 기능 완료(DoD) 최소 기준

- **설정 대화:** 사용자 입력 → 구조화 변경안 → 사용자 승인/취소 → 확정 상태 불변 또는 변경을 자동화 테스트로 확인.
- **전환 가능성:** LangChain ↔ SDK, LangGraph ↔ 기본 Python 중 해당 대체 구현이 같은 API 계약을 만족하고, 스위치 후 주요 회귀 테스트가 통과할 것.
- **공지 추천:** 추천/제외 이유가 공지 원문·설정과 연결되고, 미확인 자격과 기한을 사실로 표현하지 않으며, 미추천/누락 사례를 포함한 평가셋 결과를 기록.
- **배포 준비:** 비밀값 검출, 설치·실행 재현, API 계약, 인증/소유권 테스트 확인. 미결정 보안 정책이 있는 기능은 실제 사용자 데이터를 대상으로 서비스하지 않는다.

## 10. 미결정 사항

1. 사용자 설정·개별 추가 조건의 최종 DB 스키마와 상한/정리 정책
2. 대화 기록 보존 기간, Compaction 임계값과 맥락 품질 기준
3. Core ↔ Backend 최종 JSON·API 경로·공통 응답 형태
4. 공지 검색 인덱스/메타데이터 책임, 공통 분석 결과의 저장 위치
5. 개인별 추천 트리거 및 결과 재사용/알림 중복 방지 정책
6. Claude 모델 버전 고정, LangChain/LangGraph 구체 패키지 버전과 적용 환경 호환성·의존성 승인
7. 데이터 보존/삭제 정책, API 요청·재시도·비용 상한의 구체 값
8. 프레임워크 대체 구현을 어떤 테스트·배포 단위로 지원할지

## 11. 이 PRD를 기준으로 개발하는 규칙

- **이 문서가 제품 요구사항의 기준선**이다. 다른 채팅의 추정이나 과거 계획보다 최신 승인된 PRD를 우선한다.
- 확정되지 않은 항목을 임의 확정하지 않는다. 개발에 필요하면 작게 선택하고 결과를 명시한다.
- PRD 변경은 이유, 검증 근거, 영향 범위를 남겨 **PR로 검토한 뒤 반영**한다.
- 구현·성능·진행률은 코드·테스트 기록 없이 완료로 표시하지 않는다.
- 외부로 공개할 수 없는 제공 가이드·샘플 원본, 비밀키, 실제 사용자 정보는 저장소에 올리지 않는다.
