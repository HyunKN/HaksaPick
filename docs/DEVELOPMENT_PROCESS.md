# 개발 프로세스 — 실행 가능한 안전 규칙과 검증 (v1)

> 기준: [PRD](PRD.md). 범위: HaksaPick B 파트와 공통 Backend 연동. 이 문서는 **구현할 규칙/테스트의 체크리스트**이며, 해당 코드가 이미 존재한다는 뜻은 아니다.

## 1. 기본 원칙: 말로만 금지하지 않는다

PRD의 필수 규칙은 다음 세 단계에 동시에 나타나야 한다.

1. **런타임 강제**: 사용자가 잘못된 입력을 보내거나 LLM이 규칙을 무시해도 서버 코드가 거절/보호한다.
2. **자동 검증**: 정상·경계·악성·실패 사례를 Mock과 테스트 DB로 재현하고, 실패하면 테스트 프로세스가 0이 아닌 종료 코드로 중단한다.
3. **통합 차단**: 관련 CI 테스트 실패 시 PR을 병합하지 않도록 저장소의 필수 상태 검사(Required checks) 및 브랜치 보호 규칙을 설정한다. **설정이 실제로 적용되기 전에는 '자동 병합 차단 완료'로 보고하지 않는다.**

**절대 프롬프트 문구, AGENTS.md 또는 PR 체크박스만으로 보호가 강제된다고 주장하지 않는다.**

## 2. 요구사항 → 코드 강제 → 실패 테스트 연결표

| 불변조건 (깨져선 안 되는 규칙) | 코드에서 강제할 위치 / 방식 | 필수 실패·경계 테스트 |
|---|---|---|
| 승인 전 확정 설정 불변 | Backend는 변경안을 별도 Pending 상태로 유지하고 승인 API에서만 저장 | 사용자 채팅/Claude 출력만으로 DB 변경 불가, 승인 취소 시 동일 상태 |
| 사용자 소유 데이터만 접근 | Spring Security 인증 정보로 사용자 식별, 조회·수정 쿼리에 소유권 조건 | A 사용자 토큰으로 B 사용자의 설정/변경안 조회·수정 시 403/404 |
| 오래된 승인·중복 승인 차단 | DB 트랜잭션 + 버전 비교(optimistic lock) + 승인 요청 식별자/유일 제약 | 병렬 세션 버전 충돌, 같은 승인 재전송에도 한 번만 반영 |
| Claude·Tool 출력은 권한이 없음 | Core Pydantic 입력/출력 검사, Backend 허용된 변경 타입/ID/범위만 반영 | 가짜 condition ID, 허용되지 않은 필드/동작, 악성 tool 결과 거부 |
| 공지는 **데이터**이지 지시문이 아님 | 외부 자료를 신뢰되지 않는 컨텍스트로 분리, 도구 권한 및 DB 쓰기 제한 | 공지에 '지침 무시/설정 삭제' 포함해도 권한 없는 조작 0건 |
| 실패 시 설정 보호 | 오류/타임아웃 경로에 쓰기 없음, 예외는 명확한 실패 응답, 재시도 제한 | API 타임아웃·잘못된 JSON·스키마 오류 후 이전 DB 상태 유지 |
| 컨텍스트 압축이 확정 조건을 지우지 않음 | 확정 설정은 DB 원본 조회. 요약은 보조 자료만 사용 | 긴 대화/압축 후에도 국가장학금 제외 등 필수 조건 보존 |
| 추천 근거와 자격 불확실성 | 공지 ID·버전·출처 및 근거 존재 검사; relevance와 eligibility 필드 분리 | 없는 마감일/자격 단정 금지, 근거 없음/모름 분류 검증 |
| 사용자 정보·비밀값 최소 노출 | 환경변수/Secret 관리, 로그 마스킹, 저장 최소화·접근 분리 | API 키·개인 대화가 로그·응답·리포트에 나오지 않음 |
| 비용·무한 반복 제한 | 입력 크기/호출/재시도/도구 루프 상한, 타임아웃 | 반복 Tool Calling이 지정 한도에서 종료하고 오류를 반환 |
| 프레임워크 롤백 가능 | `LLMAdapter`, `WorkflowRunner` 공통 계약을 기반으로 구현 교체 | LangChain↔SDK, LangGraph↔Python 조합별 계약·기본 회귀 통과 |

**테스트는 각 작업에 필요한 행부터 구현한다.** 아직 개발하지 않는 추천 기능이나 다단계 실행 기능의 테스트까지 초기 단계에 억지로 만들어놓을 필요는 없다.

## 3. 각 기능의 개발 순서 (작은 단위 반복)

1. **한 기능 선택:** PRD 요구와 담당 축(Frontend/Backend/Core)을 하나 지정한다.
2. **계약 확인·확정:** [API_SPEC](API_SPEC.md)와 [DATA_MODEL](DATA_MODEL.md)의 확정 규칙/미확정 필드를 확인한다. 이번 기능의 요청·응답 스키마와 저장/비저장 필드를 합의하고, 코드·테스트와 같은 PR에서 명세를 갱신한다. 다른 팀 인터페이스는 임의 확정하지 않는다.
3. **불변조건 확인:** 위 표에서 관련 규칙 및 예상 실패 응답을 추린다. 권한·보존 정책 등이 미결정이면 먼저 결정한다.
4. **테스트 먼저 추가:** 정상 1건 + 잘못된/악성/실패 최소 1건을 Mock으로 재현한다. 테스트가 실제로 실패하는지 확인한다.
5. **코드로 강제:** Spring Boot의 권한·트랜잭션, Core의 Pydantic/도구 allowlist/한도 등 해당 실행 경계에서 검증한다.
6. **전환·회귀 확인:** LangChain/LangGraph 구현과 대체 구현이 같은 도메인 계약을 지키는지 관련 영역만 테스트한다.
7. **로컬 검증 + PR:** 재현 명령과 실제 테스트 결과를 PR 템플릿에 기록한다. 미실행 테스트는 '미실행'으로 명시한다.
8. **CI 통과 + 리뷰:** 테스트 실패·권한 우회·근거 없는 완료 주장이 있으면 병합하지 않는다. 출시 전에 관련 필수 상태 검사를 브랜치 보호 규칙으로 활성화한다.

하나의 PR은 가능하면 한 가지 사용자 흐름과 관련 테스트만 포함한다. 프레임워크 도입 자체가 아니라 **잘못된 동작이 거절되는 것**을 완료 기준에 넣는다.

## 4. 자동 검증과 CI 구현 계획 (코드 추가 시)

소스 코드가 들어오면 같은 PR 또는 선행 PR에서 실제 테스트 명령과 GitHub Actions를 함께 추가한다. **CI에서 테스트가 하나도 실행되지 않고 성공하는 빈 작업은 인정하지 않는다.**

| 구간 | 최소 자동 검증 | 구현 위치 예시 |
|---|---|---|
| Core | `poetry install`, `pytest` 기반 Pydantic/LLM 모킹/권한 없는 도구 호출·오류 주입/어댑터 계약 | `core/tests/`, `core/pyproject.toml` |
| Backend | `./gradlew test`로 승인·소유권·동시성·중복 요청·트랜잭션 검사 | `backend/src/test/` |
| API 계약 | Mock Backend↔Core JSON 호환 검사, 스키마 변경 시 실패 | `core/tests/` 및 Backend 테스트 |
| 보안·비밀 | 키/비밀 검출과 예외 로깅 점검, 의존성 취약점 검토(도구 선정 후) | `.github/workflows/` |
| E2E | 변경안 제안→사용자 승인→DB 반영과 오류 시 불변 테스트 | 별도 통합 테스트 |
| FE (해당 기능 구현 시) | `npm ci`, `npm run build`, UI 계약 관련 테스트 | `frontend/` |

- 실제 CI 파일과 Required checks 설정은 소스가 생기고 검증 명령이 확정되었을 때 추가한다.
- CI 러너의 비밀값은 사용하지 않는 Mock 테스트가 기본. 실 LLM/API 호출 기반 평가는 별도 수동/제한 환경에서 수행한다.
- 외부 서비스·네트워크 장애를 불필요하게 PR의 필수 조건으로 만들지 않는다.
- GitHub 브랜치 보호 설정은 실제 저장소에 적용·검증한 뒤 그 상태를 보고한다.

## 5. 작업 유형별 '완료' 판정

- **문서/설계:** PRD와 일치하고 확정/미결정이 분리됨. 코드 동작 완료로 계산하지 않음.
- **Core 구현:** 유효·무효 모델 응답, 실패 경로, 프레임워크 교체 테스트와 실제 실행 명령이 존재.
- **Backend 구현:** 인증·소유권, 사용자 승인, 버전 충돌, 중복 요청, 예외 시 원자성 테스트 존재.
- **추천 구현:** 원문 근거·불확실성, 누락 반례 테스트 및 평가 데이터/결과 존재.
- **통합/배포 준비:** 관련 테스트 실행/CI, API 계약, 비밀값·개인정보 보호 정책이 충족됨. 실패·미결정 항목은 미완료.

## 6. 유지 관리

- 신규 요구/버그마다 **불변조건 → 강제 코드 → 실패 테스트**의 연결을 업데이트한다.
- 기능 삭제·변경 시 해당 테스트와 계약도 함께 갱신한다. 중요 안전 테스트 삭제 시 PR에서 이유와 대체 증거를 명시한다.
- 테스트가 형식적이거나 Mock만 통과하고 실제 Backend 검증이 없다면 '보호 구현 완료'로 표시하지 않는다.
- PRD를 바꾸지 않고 안전 규칙을 약화시키는 구현 변경은 허용하지 않는다.
