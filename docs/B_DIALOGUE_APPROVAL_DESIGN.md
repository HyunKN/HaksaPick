## 1. 목적과 핵심 불변조건

사용자와 여러 번 대화하며 원하는 공지의 **포함/제외/추출·추가 조건**을 파악하고, 필요한 경우 질문한 뒤, **승인된 변경만** 저장한다.

기존 승인 규칙:
1. **확정 설정은 DB를 진실의 원천으로 사용**한다. 대화 요약, LangGraph State, LLM 출력으로 대체하지 않는다.
2. LLM은 `ask | propose | no_change`를 **제안**할 뿐 설정을 직접 저장하거나 변경하지 않는다.
3. UI에서 사용자가 변경안의 전체 내용을 **확인하고 명시적으로 승인**해야 Backend가 반영한다. 채팅의 단순 긍정은 저장 명령이 아니다.
4. Backend는 **인증/소유권/기준 설정 버전/중복 승인/원본 변경안**을 검증하고 트랜잭션으로 적용한다.
5. 사용자 정의 조건은 개별 ID를 가진 데이터로 저장한다. 새로운 조건을 만들 때마다 DB 스키마/컬럼을 변경하지 않는다.
6. 확정 상태를 손상시킬 수 있는 오류 경로(타임아웃, 불완전 JSON, 인젝션, 버전 충돌)에서는 쓰기를 실행하지 않는다.
7. B의 LangChain·LangGraph는 모듈화된 Core 내부 실행 수단이지 최종 저장 권한 주체가 아니다.

## 2. 사용자 흐름과 LangGraph 분기

```text
FE 채팅 입력
 → Spring Backend: 인증, 확정 설정과 버전, 관련 최근 대화, pending 제안 조회
 → Core: context_build → LangChain/Claude structured interpret
 → Pydantic 검증
 → LangGraph 분기:
    ├─ ask: 추가 질문 반환, 확정 설정 변경 없음
    ├─ no_change: 일반 답변/정보 제공, 변경 없음
    └─ propose: 추가/수정/삭제 작업을 묶은 변경안 반환
 → Backend: 제안 검증·보관 + FE로 표시
 → 사용자: 승인 / 편집 / 취소
    ├─ 승인: Backend의 트랜잭션·소유권·버전 검증 후 반영
    ├─ 편집: 새 검토용 제안 생성(기존 서버 저장 제안 무단 변경 금지)
    └─ 취소: pending 제안 폐기, 확정 설정 불변
```

**개발 기본안 — 한 번에 여러 변경 처리:** 한 문장으로 `include: 현장실습 추가`, `exclude: 국가장학금 신청 안내 추가`, `기존 조건 수정` 등을 요청하면 **하나의 proposal에 배열로 묶어 미리보기**하고 한 번에 승인한다. 서로 충돌하거나 참조가 모호한 작업은 먼저 질문한다. 데이터가 확정되기 전에 일부 연산만 저장하지 않는다.

**기존 결정과의 경계:** 기본 학적 정보(학년·학과·재학 상태)는 PRD대로 **폼 기반 입력**이 기본이며, 이 문서의 LLM 제안/승인 계약을 자동으로 강제하는 대상은 *대화 기반 관심 조건 변경*이다. 폼 갱신 역시 해당 사용자의 최신 설정과 버전 일관성을 유지해야 한다.

## 3. 어떤 경우 질문하고 어떤 경우 제안하는가?

| 상황 | Core 출력 `decision` | 동작 |
|---|---|---|
| '인턴 모집도 추가해줘'이고 대상·범위가 명확 | `propose` | 조건 추가 제안, 승인 전 저장 없음 |
| '그 조건 삭제해줘'인데 후보 조건이 2개 이상 | `ask` | 무엇을 삭제할지 질문, 임의 삭제 금지 |
| '장학금 신청 안내는 제외, 취업 프로그램은 포함'처럼 명확한 복수 요청 | `propose` | 추가/제외 작업을 한 proposal로 보여줌 |
| 같은 공지 범위에 필수 포함/제외가 충돌 | `ask` | 적용 범위 또는 예외 허용 여부 질문 |
| 이미 명확한 확정 조건을 다시 설명 | `no_change` 또는 의미 있는 수정만 `propose` | 중복 작업/반복 질문 최소화 |
| '고마워', 서비스 설명 요청 | `no_change` | 확정 설정 불변 |
| '응', '좋아'만 보내고 현재 pending 존재 | `no_change` / UI 안내 | **채팅으로 자동 승인하지 않음**. 승인 UI로 안내 |
| 모델 응답 구조 불량·타임아웃 | 오류 | 성공 또는 새 제안으로 위장하지 않음 |

**질문 정책:** ① 변경 대상이 둘 이상이거나 ② 필수 제약/제외 범위가 모호하거나 ③ 서로 충돌하는 조건이 있는 등 **정답이 실제로 달라지는 모호함**만 질문한다. 이미 저장된 사실을 반복 질문하지 않는다. 질문은 가능하면 하나의 짧은 메시지로 사용자 결정을 요구한다.

질문에 대한 후속 답변은 Backend가 제공하는 **미해결 질문 ID/문맥 + 확정 설정 원본**으로 해석한다. Graph 실행 Checkpoint를 영구 저장하지 않아도 MVP의 다중 턴을 처리할 수 있다.

## 4. Core 입출력 도메인 계약 (B 내부 제안)

Core는 신뢰 가능한 내부 Backend 호출로 입력을 받되, 사용자 메시지와 외부 자료는 여전히 신뢰되지 않는 데이터다. Backend 인증 사용자 ID는 사용자 텍스트/LLM 결과가 임의로 지정하게 하지 않는다.

**Core 입력 후보:**

```json
{
  "conversation_id": "conversation-1",
  "message_id": "message-9",
  "message": "현장실습은 포함하고 국가장학금 신청 안내는 제외해줘",
  "preference_version": 3,
  "confirmed_preferences": {
    "conditions": []
  },
  "recent_history": [],
  "unresolved_question": null,
  "pending_proposal": null,
  "trace_id": "trace-101"
}
```

**Core 출력 후보:**

```json
{
  "decision": "propose",
  "assistant_message": "현장실습 포함, 국가장학금 신청 안내 제외 조건을 추가할까요?",
  "proposed_changes": [
    {
      "operation": "add",
      "target_condition_id": null,
      "condition": {
        "scope": "notices",
        "polarity": "include",
        "strength": "preferred",
        "text": "현장실습 모집"
      }
    },
    {
      "operation": "add",
      "target_condition_id": null,
      "condition": {
        "scope": "notices",
        "polarity": "exclude",
        "strength": "required",
        "text": "국가장학금 신청 안내"
      }
    }
  ],
  "clarification": null,
  "trace_id": "trace-101"
}
```

- `proposed_changes`는 `decision=propose`일 때만 비어 있지 않도록 구조 검증한다.
- `ask`일 때는 `clarification`의 질문 내용과 해결해야 할 모호함/후속 답변을 연결할 식별자를 반환하며 변경안은 비워 둔다.
- `no_change`일 때는 변경안을 비워 둔다.
- `add/update/remove`의 대상 조건은 `condition_id`와 소유권/현재 버전으로 검증한다. 새 조건의 ID는 서버가 발급한다.
- `scope`, `polarity`, `strength`, `text`는 **후보 필드**. 제안 내용에 권한·상태 변경·서버 내부 필드가 있으면 거부한다.
- Core 결과의 자유 서술 `assistant_message`는 **표시용**, 변경할 실제 작업 배열과 별개. UI는 배열 기반 변경 미리보기로 승인받는다.
- Backend/FE의 성공/오류 응답 래퍼와 URL은 기존 `API_SPEC.md`의 **미확정 제안 경로**를 그대로 참조하며 여기서 재정의하지 않는다.

## 5. 변경안 보관과 DB 개념 모델 (아직 실제 테이블 미생성)

DB가 아직 생성되지 않았으므로 아래는 B 측 구현을 위한 논리적 데이터 책임 초안이다.

| 개념 엔티티 | 권장 속성 | 이유 |
|---|---|---|
| `preference_sets` (가칭) | 서버 인증 소유자 ID, `version`, 갱신 시점 | 확정 조건 집합·낙관적 버전 관리 |
| `preference_conditions` (가칭) | `condition_id`, 사용자 소유자, `scope`, `polarity`, `strength`, `text`, 활성 여부 | 유연한 조건 추가·수정·삭제; 구조/인덱스는 DB 합의 후 결정 |
| `pending_proposals` (가칭) | `proposal_id`, 서버 소유자, `base_version`, 변경 연산 배열, 상태, 생성 시각, 원본 내용 해시, 처리 시각 | 화면 미리보기와 실제 승인된 변경안 동일성 |
| `dialogue_sessions` 또는 경량 문맥 (가칭) | 대화 ID, 소유자, 마지막 미해결 질문/참조, 필요한 최근 문맥 | 다중 턴 재질문/이어하기. LangGraph Checkpoint와 별도 |
| `approval_events` (선택 구조) | `proposal_id`, 승인 요청 식별자, 처리 결과, 적용 버전 | 중복 요청·재시도에 대한 일관된 응답 및 감사 흔적 |

**선택 구현:** 설정 버전을 담은 행에 대해 조건부 `UPDATE ... WHERE version = base_version` / 적절한 행 잠금과 한 트랜잭션으로 모든 연산을 적용한다. 성공하면 `version + 1`, proposal을 `approved`로 변경한다. 불일치하면 원자적으로 실패한다. *구체 SQL/제약/RLS는 Supabase 실제 인증·소유권 설계에 맞춰 확정해야 한다.*

- `pending`/ `approved`/ `cancelled`/ `expired`/ `conflicted` 상태 예시.
- 새 제안이 생성될 때 기존 pending 제안을 어떻게 처리할지: 동일 기능/설정 대상의 이전 제안은 **대체 또는 취소**하고 UI에서 낡은 제안 승인 불가로 구현하는 기본안.
- 만료 기간, 보존/삭제 기간, 대화 기록 저장 범위는 실제 사용자 데이터를 수집하기 전에 팀이 결정한다. 현재 임의 만료값이나 개인정보 무제한 저장 정책을 확정하지 않는다.
- 대화 요약·LangGraph State는 개인 설정의 단독 저장원이 아니다.

## 6. Backend 승인 처리 계약 — 동작 순서

1. JWT 인증 후 서버 사용자 식별. 요청에 임의의 `user_id`를 받아 권한을 부여하지 않는다.
2. 서버 저장된 `proposal_id` 조회 및 소유자 일치 확인. 원래 제안 `operations`와 클라이언트 승인 미리보기의 일치 보장.
3. proposal 상태 `pending` 확인. 만료·취소·기처리·재생 요청이면 거절하거나 기존 승인 결과를 **멱등** 반환한다.
4. 현재 설정 버전과 `base_version` 비교. 다르면 **충돌 응답**과 최신 설정 갱신/재검토 경로 제공. 조용히 병합하지 않는다.
5. 모든 `target_condition_id`가 인증 사용자 소유이며 허용된 `operation`인지 검증. 여러 연산 중 하나라도 불법이면 **전부 실패**.
6. 트랜잭션에서 조건 반영 + 버전 증가 + 제안 승인 상태 + 중복 실행 기록 원자적 커밋.
7. UI에 저장 후의 설정 버전과 반영된 조건을 **DB 조회값으로** 반환. LLM이 주장한 '저장 완료' 메시지를 그대로 믿지 않는다.

**오류 범주 후보:** `validation_error`, `unauthorized`, `forbidden`, `proposal_not_found`, `proposal_not_pending`, `version_conflict`, `llm_unavailable`, `invalid_llm_output`. 팀 공통 HTTP 매핑/래퍼 확정 전에는 내부 오류 분류로만 사용한다.

### 동시 수정 예시

- A 창은 `base_version=3`으로 `cond-01` 삭제 제안을 받아 둠.
- B 창은 동일 버전으로 `cond-01` 수정을 승인하여 최신 버전이 `4`가 됨.
- A 창의 삭제 승인은 **거절**. 최신 상태를 읽고 다시 검토해야 한다.
- 승인 버튼의 더블클릭·네트워크 재전송은 **한 번만** 반영된다.

## 7. 프론트엔드 화면 요소 (B 기능 연결)

1. **채팅**: 현재 메시지와 Claude 답변 표시. 일반 답변/추가 질문/변경 제안을 UI에서 구분.
2. **추가 질문**: 무엇이 모호한지 명확하게 안내. 현재 입력으로 확정 설정을 변경하지 않음.
3. **변경안 미리보기 카드**: `추가/수정/삭제` 작업과 대상 조건, 포함/제외 및 필수/선호 범위를 모두 표시.
4. **승인/편집/취소**: 승인 버튼으로만 Backend 승인 API 호출. 편집 시 서버 검증된 새 변경안 생성; 취소 시 pending 상태 닫기.
5. **충돌·오류**: 버전 충돌 시 최신 조건과 변경안을 나란히 비교하거나 재제안. 네트워크 오류에서 '저장 완료' 표시 금지.
6. **확정 조건 목록**: DB에서 확정된 최신 조건과 버전을 조회해 표시. 미승인 채팅 텍스트는 이 목록에 보이지 않음.

## 8. 기능별 Mock / 계약 / 안전 테스트

| ID | 입력/상황 | 기대 결과 |
|---|---|---|
| D01 | 포함 조건 하나 명확히 요청 | `propose(add)`, 승인 전 DB 불변 |
| D02 | 포함 + 필수 제외를 한 문장으로 요청 | 배열 변경안 하나, 모든 연산 검증 |
| D03 | '그 조건 삭제' 참조가 여러 개 | `ask`, 삭제 임의 수행 금지 |
| D04 | 일반 질문/인사 | `no_change`, 상태 불변 |
| D05 | 기존 제외 유지 + 새 관심 추가 | 기존 조건 완전 보존 |
| D06 | 승인 버튼이 아닌 단순 채팅 '응' | 승인 저장 없음 |
| D07 | 승인 이후 정상 저장 | 정확한 연산 적용, 버전 +1 |
| D08 | 서로 다른 세션에서 같은 기준 버전 승인 | 하나만 성공, 나머지 충돌 |
| D09 | 동일 제안 승인 재전송 | 중복 저장 없음; 일관 응답 |
| D10 | 타인 proposal/condition_id 승인 시도 | 소유권 차단 |
| D11 | LLM 응답 JSON 오류/타임아웃 | 오류로 반환, 확정 설정 불변 |
| D12 | 이전 질문에 대한 후속 답변 | 참조하는 질문 ID/현재 설정 기반 처리 |
| D13 | 제안 생성 후 기존 확정 설정 변경 | 낡은 proposal 승인 차단 |
| D14 | 악성 채팅 '인증 없이 설정 삭제' | LLM 출력이 DB 권한을 획득하지 못함 |
| D15 | LangChain↔SDK, LangGraph↔기본 Python 교체 | 동일 도메인 계약/승인 불변조건 유지 |

기능 단위로 최소 정상+실패 테스트를 함께 추가한다. *본 표는 설계된 기대값이지 테스트 PASS 결과가 아니다.*

## 9. 당장 구현에 착수할 수 있는 최소 범위

- Core: `schemas/condition.py` + `schemas/dialogue.py`, `dialogue/intent.py`, `dialogue/proposal.py`, `dialogue/workflow.py`, `llm/langchain_adapter.py`와 Mock 단위 테스트.
- Backend: 저장 전 `pending_proposal` 생성/조회/승인/취소 API + 소유권/버전/멱등 트랜잭션 테스트.
- FE: 채팅 분기/추가 질문/변경안 미리보기/명시적 승인/충돌 처리.
- 확정 전 A 파트 실제 공지 스키마는 이 기능 Mock 개발에 필요하지 않음.

**연동 때 실제로 맞춰야 할 것:** 공통 사용자 인증키, Supabase 테이블/RLS, 공통 API 응답 래퍼·URL, 대화/제안 보존기간 및 민감 정보 취급, 모델/프롬프트 버전. 이들 값이 아직 미정이어도 Mock 기반 Core 대화 테스트는 개발 가능하다.

**완료 판정:** 문서 자체로는 *설계 산출물 초안*이며, 실제 구현/권한 검증/CI 테스트가 끝났다고 보고하지 않는다.
